# 前端与角色边界规划

## 1. 目标

明确 `kms-user`、`kms-generate/front`、`kms-updatedel/front`、`kms-distribute` 的职责边界，避免统一前台建设后误删管理员后台能力。

本规划的核心结论：

1. 普通用户前台统一到 `kms-user`
2. 管理员后台按系统保留
3. 账号体系统一，前端界面按角色分层
4. 普通用户可按功能发起临时提权申请，由对应系统管理员审批

## 2. 角色分层

### 2.1 普通用户

定位：业务使用者。

主要诉求：

1. 注册账号
2. 登录系统
3. 发起密钥生成
4. 发起密钥更新
5. 发起密钥回收
6. 查看分发记录与个人结果
7. 对受限功能发起临时权限申请

前端入口：

1. `kms-user`

不再作为主入口的前端：

1. `kms-generate/front` 中面向普通用户的页面
2. `kms-updatedel/front` 中面向普通用户的页面

### 2.2 临时授权用户

定位：仍然属于普通用户，但因审批通过，在限定时间或限定流程内获得更高功能权限。

主要特征：

1. 默认不直接注册为该类型用户
2. 通过权限申请获得临时提权
3. 仅获得被批准的目标能力
4. 完成操作后回退为普通用户
5. 不进入系统管理员后台

### 2.3 生成系统管理员

定位：生成域后台管理者。

主要诉求：

1. 管理生成链路配置
2. 管理生成记录
3. 审计生成行为
4. 处理生成侧异常和运维事项

前端入口：

1. `kms-generate/front`

### 2.4 生命周期系统管理员

定位：更新、回收、审批域后台管理者。

主要诉求：

1. 管理更新任务
2. 管理回收任务
3. 配置自动更新策略
4. 审批和回退权限申请

前端入口：

1. `kms-updatedel/front`

### 2.5 分发系统管理员

定位：分发域后台管理者。

当前状态：

1. 暂未形成完整独立后台工程
2. 后续视分发管理诉求决定是否建设独立管理员前端

## 3. 前端职责划分

### 3.1 `kms-user`

只承接普通用户能力，不承接系统级后台管理能力。

应包含：

1. 统一登录
2. 统一注册
3. 工作台
4. 密钥生成与生成记录
5. 公共库与公共参数查询
6. 密钥更新、密钥回收、自动更新
7. 单条密钥安全分析与结果回执
8. 分发记录查询
9. 权限不足提示
10. 权限申请入口
11. 我的申请记录
12. 回退入口

不应包含：

1. 生成系统级参数配置
2. 生命周期系统审批后台全量管理能力
3. 各系统专属运维管理页
4. 系统级菜单、角色、审计后台

### 3.2 `kms-generate/front`

定位为生成系统管理员后台。

应保留：

1. 管理员首页
2. 生成记录管理
3. 生成配置管理
4. 生成审计能力
5. 生成侧系统管理页面
6. 算法图解与演示

可逐步移出：

1. 普通用户注册页
2. 普通用户登录页
3. 普通用户密钥生成入口
4. 普通用户个人查询页

### 3.3 `kms-updatedel/front`

定位为生命周期系统管理员后台。

应保留：

1. 更新任务管理
2. 回收任务管理
3. 自动更新配置
4. 单条密钥安全分析
5. 权限审批
6. 回退管理
7. 生命周期侧系统管理页面

可逐步移出：

1. 普通用户登录页
2. 普通用户发起更新入口
3. 普通用户发起回收入口
4. 普通用户个人查询页

## 4. 账号与权限模型

### 4.1 统一部分

建议统一：

1. `sys_user`
2. `sys_role`
3. `sys_user_role`
4. `sys_menu` 中的角色授权关系

效果：

1. 用户只注册一次
2. 同一用户在三套系统身份一致
3. `admin` 可按授权访问多个后台或前台
4. 普通用户的提权记录可跨系统统一关联到同一用户身份

### 4.2 分离部分

建议分离：

1. 普通用户前台菜单
2. 生成管理员后台菜单
3. 生命周期管理员后台菜单
4. 分发管理员后台菜单
5. 各系统的权限申请审批流

不要把所有菜单混在一个入口里直接暴露给所有角色。

### 4.3 提权模型

> ⚠️ **本节已被 `doc/kms-restructure-plan.md` 取代（Q2 / D13）。**
> 该计划把角色由 3 级收成 **2 级**，并删除了"生成域 查看公共密钥列表"这一申请项（D1）。
> 下表记录的是被取代的历史设计，保留仅为追溯，**不要按它实现**。
> 现行模型见 `doc/kms-restructure-plan.md` §3.4。

历史设计（已废弃）：保留 `role_level` 分层思路，共 3 级——

1. `0`：管理员
2. `1`：临时授权用户或中级用户 ← **已废弃**
3. `2`：普通用户

**现行模型（2 级）**：

| 级别 | 含义 |
|---|---|
| `0` | 管理员 |
| `2` | 普通用户 |

判据全部收敛为 `role_level <= 0` 一个表达式。等级 `1` 的唯一用途是放行
`PUBLIC_KEY_LIST`，该功能已整体删除，故等级 `1` 不再存在（存量数据实测为 0 个账号）。

规则如下：

1. 注册用户默认是普通用户
2. 普通用户访问受限功能时，前台提示权限不足
3. 用户可直接在 `kms-user` 发起权限申请
4. 申请需带上目标功能、目标系统、申请理由
5. 申请由对应系统管理员审批，不走无关系统后台
6. 审批通过后，用户临时获得目标权限
7. 用户完成操作后需手动回退，或由系统自动回退

该模型与旧版一致：不是把普通用户永久升成管理员，而是按业务临时提权。

> 补充（P1 实施时确认）：**临时授权不再改写 `role_level`**。
> 全仓库原有**两处**会改写它：生成域的 `PermissionRequestServiceImpl.approve()`
> （随 D1 删除整套子系统而移除），以及**更新域的 `PermissionRequestService`**
> （`approve()` 写 `requestLevel`=0，`rollback()` 写 2 或已废弃的 1）。
> 后者是真缺陷，已在 P1 修掉，连死掉的 `SysUserMapper.updateRoleLevel` 一并删除。
> 所以现在 `role_level` 是一个**纯静态的账号属性**，临时权限只由
> `permission_request` 表 + `hasActiveTemporaryPermission()` 判定。
> 这一点对 D9 很关键：否则一次审批通过就会把普通用户的 `role_level` 抬到 0，
> 而 D9 的分流判据正是 `role_level <= 0`，用户下次登录会被直接送进管理控制台。

### 4.4 需要申请的功能范围

> ⚠️ 同样已被 `doc/kms-restructure-plan.md` 取代。现行只保留 **1 项**申请能力。

现行（D1 + D2）：**只剩生命周期域「密钥自动更新」**。

1. ~~生成域 `查看公共密钥列表`~~ —— **已整体删除**（D1）。该功能会让一个用户读到
   其他用户的公钥集合，与"密钥不外泄"的目标冲突；其审批项、接口、服务、
   Mapper、定时任务与前端页面均已移除。
2. 生命周期域 `密钥自动更新`
   - `role_level = 0` 永久放行，否则需临时授权
   - 申请入口已从独立的"权限管理"页迁到 **「更新与回收」页的按钮 + 弹窗**（D2）

对应审批归属：

1. `密钥自动更新` 由生命周期系统管理员在 `kms-updatedel/front` 的「权限审批」页审批
   （该页只查 `system_code = 'lifecycle'`，生成域遗留申请已由迁移脚本清理）

## 5. 推荐菜单模型

### 5.1 普通用户菜单

放在 `kms-user`：

1. 工作台
2. 密钥生成
3. 密钥更新
4. 密钥回收
5. 我的密钥
6. 分发记录
7. 个人中心
8. 权限申请
9. 我的申请记录
10. 权限回退

说明：`权限申请` 中第一阶段仅开放以下申请项：

1. 查看公共密钥列表
2. 密钥自动更新

### 5.2 生成管理员菜单

放在 `kms-generate/front`：

1. 生成首页
2. 生成记录管理
3. 生成配置
4. 生成审计
5. 系统管理
6. 生成域权限申请审批

### 5.3 生命周期管理员菜单

放在 `kms-updatedel/front`：

1. 生命周期首页
2. 更新管理
3. 回收管理
4. 自动更新配置
5. 权限审批
6. 回退管理
7. 系统管理

### 5.4 分发管理员菜单

6. 分发域权限申请审批

## 6. 迁移策略

### 6.1 第一阶段

1. 保留 `kms-generate/front` 和 `kms-updatedel/front`
2. 新建或完善 `kms-user` 普通用户统一前台
3. 将普通用户页面逐步迁入 `kms-user`
4. 将权限申请、申请记录、回退入口一并迁入 `kms-user`
5. 管理员继续使用各自系统后台

### 6.2 第二阶段

> ⚠️ 第 3 条**已被 `doc/kms-restructure-plan.md` 的 D9 明确否决**，不要实现。
> 原话是"为管理员登录后提供明确的系统后台跳转入口"——也就是在用户前台顶部放一个
> "进入管理控制台"按钮。D9 的决策是：**只有一个登录入口，登录后按 `role_level` 分流**，
> 管理员直接落在管理控制台，普通用户留在用户前台，**不额外提供跳转按钮**。
> 该按钮曾在 `kms-user/front/src/layout/components/Navbar.vue` 实现过，P1 已删除。

1. 从各系统前端中移除重复的普通用户入口
2. 保留管理员所需页面和系统管理能力
3. ~~为管理员登录后提供明确的系统后台跳转入口~~ → **改为按角色自动分流**（D9）：
   `role_level <= 0` 登录后整页跳转管理端；普通用户访问管理端会被整页跳回用户前台。
   两个应用同源且共用 `Admin-Token` Cookie，因此无需二次登录。
4. 将审批页面固定在对应系统后台中处理

### 6.3 第三阶段

1. 评估是否还需要各系统内置普通用户路由
2. 若无历史兼容需求，可下线重复普通用户页面
3. 管理员后台持续独立维护

## 7. 判断标准

满足以下条件时，说明边界划分合理：

1. 普通用户只需在 `kms-user` 注册和登录一次
2. 普通用户不需要再进入各系统独立前端完成日常业务
3. 生成管理员仍可在 `kms-generate/front` 完成系统管理
4. 生命周期管理员仍可在 `kms-updatedel/front` 完成系统管理
5. 共用用户体系，但不同角色看到的菜单和入口清晰分离
6. 普通用户可对受限功能发起申请
7. 申请只在对应系统后台审批
8. 审批通过后用户可临时使用目标能力，并可回退
