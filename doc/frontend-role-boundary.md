# 前端与角色边界规划

## 1. 目标

明确 `kms-user`、`kms-generate/front`、`kms-updatedel/front`、`kms-distribute` 的职责边界，避免统一前台建设后误删管理员后台能力。

本规划的核心结论：

1. 普通用户前台统一到 `kms-user`
2. 管理员后台按系统保留
3. 账号体系统一，前端界面按角色分层
4. 普通用户可按功能发起临时提权申请，由对应系统管理员审批

## 2. 角色分层

### 2.1 普通用户

定位：业务使用者。

主要诉求：

1. 注册账号
2. 登录系统
3. 发起密钥生成
4. 发起密钥更新
5. 发起密钥回收
6. 查看分发记录与个人结果
7. 对受限功能发起临时权限申请

前端入口：

1. `kms-user`

不再作为主入口的前端：

1. `kms-generate/front` 中面向普通用户的页面
2. `kms-updatedel/front` 中面向普通用户的页面

### 2.2 临时授权用户

定位：仍然属于普通用户，但因审批通过，在限定时间或限定流程内获得更高功能权限。

主要特征：

1. 默认不直接注册为该类型用户
2. 通过权限申请获得临时提权
3. 仅获得被批准的目标能力
4. 完成操作后回退为普通用户
5. 不进入系统管理员后台

### 2.3 生成系统管理员

定位：生成域后台管理者。

主要诉求：

1. 管理生成链路配置
2. 管理生成记录
3. 审计生成行为
4. 处理生成侧异常和运维事项

前端入口：

1. `kms-generate/front`

### 2.4 生命周期系统管理员

定位：更新、回收、审批域后台管理者。

主要诉求：

1. 管理更新任务
2. 管理回收任务
3. 配置自动更新策略
4. 审批和回退权限申请

前端入口：

1. `kms-updatedel/front`

### 2.5 分发系统管理员

定位：分发域后台管理者。

当前状态：

1. 暂未形成完整独立后台工程
2. 后续视分发管理诉求决定是否建设独立管理员前端

## 3. 前端职责划分

### 3.1 `kms-user`

只承接普通用户能力，不承接系统级后台管理能力。

应包含：

1. 统一登录
2. 统一注册
3. 工作台
4. 密钥生成与生成记录
5. 公共库与公共参数查询
6. 密钥更新、密钥回收、自动更新
7. 单条密钥安全分析与结果回执
8. 分发记录查询
9. 权限不足提示
10. 权限申请入口
11. 我的申请记录
12. 回退入口

不应包含：

1. 生成系统级参数配置
2. 生命周期系统审批后台全量管理能力
3. 各系统专属运维管理页
4. 系统级菜单、角色、审计后台

### 3.2 `kms-generate/front`

定位为生成系统管理员后台。

应保留：

1. 管理员首页
2. 生成记录管理
3. 生成配置管理
4. 生成审计能力
5. 生成侧系统管理页面
6. 算法图解与演示

可逐步移出：

1. 普通用户注册页
2. 普通用户登录页
3. 普通用户密钥生成入口
4. 普通用户个人查询页

### 3.3 `kms-updatedel/front`

定位为生命周期系统管理员后台。

应保留：

1. 更新任务管理
2. 回收任务管理
3. 自动更新配置
4. 单条密钥安全分析
5. 权限审批
6. 回退管理
7. 生命周期侧系统管理页面

可逐步移出：

1. 普通用户登录页
2. 普通用户发起更新入口
3. 普通用户发起回收入口
4. 普通用户个人查询页

## 4. 账号与权限模型

### 4.1 统一部分

建议统一：

1. `sys_user`
2. `sys_role`
3. `sys_user_role`
4. `sys_menu` 中的角色授权关系

效果：

1. 用户只注册一次
2. 同一用户在三套系统身份一致
3. `admin` 可按授权访问多个后台或前台
4. 普通用户的提权记录可跨系统统一关联到同一用户身份

### 4.2 分离部分

建议分离：

1. 普通用户前台菜单
2. 生成管理员后台菜单
3. 生命周期管理员后台菜单
4. 分发管理员后台菜单
5. 各系统的权限申请审批流

不要把所有菜单混在一个入口里直接暴露给所有角色。

### 4.3 提权模型

参考旧版实现，推荐保留 `role_level` 分层思路：

1. `0`：管理员
2. `1`：临时授权用户或中级用户
3. `2`：普通用户

规则如下：

1. 注册用户默认是普通用户
2. 普通用户访问受限功能时，前台提示权限不足
3. 用户可直接在 `kms-user` 发起权限申请
4. 申请需带上目标功能、目标系统、申请理由
5. 申请由对应系统管理员审批，不走无关系统后台
6. 审批通过后，用户临时获得目标权限
7. 用户完成操作后需手动回退，或由系统自动回退

该模型与旧版一致：不是把普通用户永久升成管理员，而是按业务临时提权。

### 4.4 需要申请的功能范围

新系统中，哪些功能必须走申请流程，优先参考旧版已实际落地的能力，不额外扩大范围。

旧版已明确落地的申请功能如下：

1. 生成域 `查看公共密钥列表`
   - 旧版要求 `role_level <= 1`
   - 也就是普通用户需要先申请到中级用户后才能访问
2. 生命周期域 `密钥自动更新`
   - 旧版要求 `role_level = 0`
   - 也就是普通用户需要先申请到管理员级别后才能访问

落地原则：

1. 第一阶段只保留上述两类申请能力
2. 其他功能如果后续需要申请，必须按业务域单独评审后再加
3. 不把所有高权限页面都默认纳入申请范围
4. 审批后台必须按系统归属处理

对应审批归属建议：

1. `查看公共密钥列表` 由生成系统管理员在 `kms-generate/front` 审批
2. `密钥自动更新` 由生命周期系统管理员在 `kms-updatedel/front` 审批

## 5. 推荐菜单模型

### 5.1 普通用户菜单

放在 `kms-user`：

1. 工作台
2. 密钥生成
3. 密钥更新
4. 密钥回收
5. 我的密钥
6. 分发记录
7. 个人中心
8. 权限申请
9. 我的申请记录
10. 权限回退

说明：`权限申请` 中第一阶段仅开放以下申请项：

1. 查看公共密钥列表
2. 密钥自动更新

### 5.2 生成管理员菜单

放在 `kms-generate/front`：

1. 生成首页
2. 生成记录管理
3. 生成配置
4. 生成审计
5. 系统管理
6. 生成域权限申请审批

### 5.3 生命周期管理员菜单

放在 `kms-updatedel/front`：

1. 生命周期首页
2. 更新管理
3. 回收管理
4. 自动更新配置
5. 权限审批
6. 回退管理
7. 系统管理

### 5.4 分发管理员菜单

放在分发后台：

1. 分发首页
2. 分发记录管理
3. 分发详情查询
4. 分发配置
5. 分发审计
6. 分发域权限申请审批

## 6. 迁移策略

### 6.1 第一阶段

1. 保留 `kms-generate/front` 和 `kms-updatedel/front`
2. 新建或完善 `kms-user` 普通用户统一前台
3. 将普通用户页面逐步迁入 `kms-user`
4. 将权限申请、申请记录、回退入口一并迁入 `kms-user`
5. 管理员继续使用各自系统后台

### 6.2 第二阶段

1. 从各系统前端中移除重复的普通用户入口
2. 保留管理员所需页面和系统管理能力
3. 为管理员登录后提供明确的系统后台跳转入口
4. 将审批页面固定在对应系统后台中处理

### 6.3 第三阶段

1. 评估是否还需要各系统内置普通用户路由
2. 若无历史兼容需求，可下线重复普通用户页面
3. 管理员后台持续独立维护

## 7. 判断标准

满足以下条件时，说明边界划分合理：

1. 普通用户只需在 `kms-user` 注册和登录一次
2. 普通用户不需要再进入各系统独立前端完成日常业务
3. 生成管理员仍可在 `kms-generate/front` 完成系统管理
4. 生命周期管理员仍可在 `kms-updatedel/front` 完成系统管理
5. 共用用户体系，但不同角色看到的菜单和入口清晰分离
6. 普通用户可对受限功能发起申请
7. 申请只在对应系统后台审批
8. 审批通过后用户可临时使用目标能力，并可回退
