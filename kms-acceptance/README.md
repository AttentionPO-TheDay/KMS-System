# kms-acceptance

KMS 验收与压测系统。

## 当前定位

Demo 管理端唯一的验收入口。页面只展示八项验收结论，普通环境不再作为验收入口。

## 当前目录

1. `front/`：验收矩阵，触发性能/攻击用例，录入节点侧预分配证据
2. `backend/`：Go 后端，负责执行 `wrk`、安全用例、阈值判断和证据持久化

## 当前内置验收项

1. 无证书密钥生成速率 > 100000 TPS（SSCL 最快路径）
2. 预分配密钥速率 > 50 条/秒（节点侧 SM4 + Kyber + Falcon）
3. 密钥更新速率 ≥ 5000 TPS
4. 异常密钥回收速率 ≥ 5000 TPS
5. 异常密钥回收率 ≥ 98%
6. 密钥生成攻击防御 ≥ 3 类
7. 量子威胁模拟防御 ≥ 3 类
8. 网络攻击防御 ≥ 5 类

## 当前口径说明

1. 前端开发环境默认将 `/acceptance-api` 代理到 `http://127.0.0.1:9090`
2. 网关部署环境通过 `/acceptance-api/` 转发到验收后端
3. 生成、更新场景通过 Go 接口执行；异常回收速率与回收率调用节点健康扫描与自动回收服务。
4. 更新复用生成系统中已准备的 SM2 验收密钥池；异常回收速率与回收率自行准备隔离样本，无需先执行生成压测。
5. 更新逐钥核验版本递增且材料指纹改变；异常回收率按最终回收成功数 / 实际发起回收密钥数计算。
6. 预分配证据由节点侧产生，管理端只保存吞吐值、时间和证据说明，不接触节点私钥
7. 量子项目是协议层威胁模拟，不宣称真实量子计算机实测

## 固定 6000 把密钥更新验收

`update-tps` 复用生成系统中已准备的 6000 把有效 SM2 验收密钥，每把只提交一次更新。
从同一验收用户的有效 SM2 验收密钥中取最新 6000 把；生成速率测试仍用 SSCL，其时间窗口不限制独立的 SM2 更新池。
不足 6000 把时提示不足，不隐式生成。内部取池接口在 SQL 中按归属、有效状态、算法筛选并 LIMIT 6000，仅读取元数据。
更新采用固定数量并发请求，不依赖 wrk，不按 5000×5 秒索取 25000 把，也不循环提交相同密钥。
每轮、每钥使用独立幂等标识；重复受理响应不计入新受理成功。

实际更新速率 = 数据库更新完成数 / 从首次提交到数据库核验的耗时，包含排队和状态查询，排除取池、初始快照准备及异步上链等待。
完成要求版本递增且材料指纹改变；证据版本为 2，旧的仅核验版本号的结果需重测。
新材料、旧版本历史、审计记录与后续任务同事务持久化。后台从 `key_update_outbox` 处理证明及上链投递，失败保留重试，不阻塞更新完成。

消费者每事务最多处理 500 把，通过 MySQL 8.0.21+ 的 `JSON_TABLE` 绑定批量参数，减少动态 SQL 解析；后台证明任务在更新事务活跃时让出资源，空闲后继续处理持久化事件。Go 消息入口将尾部请求的定时缓冲缩短为 20 ms。

更新 Java 镜像默认使用 2–4 GiB 堆、G1 和 8 个并行 / 2 个并发 GC 工作线程，可通过 `JAVA_OPTS` 覆盖。MySQL 配置将 InnoDB 缓冲池设为 2 GiB；事务刷盘及 binlog 持久化要求保持不变。实测记录见 [SM2 更新验证](verification/sm2-update-20261021.md)。
升级需执行 `kms-ops/mysql/init/58_key_update_outbox.sql`；更新 Kafka 消费者批量落库，保留用户存在及密钥归属校验。
提交完成后最多等待 60 秒核验版本；等待耗时计入实际更新速率，不会把慢批次视为速率达标。
请求受理速率单独展示，不用于代替实际更新速率。目标仍为 ≥5000 条/秒，同时保留版本更新完成率核验和逐钥归档。

## 异常密钥回收验收

`revoke-tps` 和 `revoke-rate` 各自在连接私有的 MySQL 临时表中写入 6000 把 ACTIVE 异常公钥登记记录，
分别覆盖公钥缺失、摘要缺失和公钥与摘要不匹配。另有 3 把正常密钥和 1 把物化列
不一致的仅告警密钥作为对照。随后执行生产 `auto_revoke_service.scan_once()`，
逐钥核对检测规则、REVOKED 状态和审计结果，并验证关联池项、会话和失效记录。
`revoke-tps` 要求全部异常回收且速率 ≥5000 把/秒；`revoke-rate` 要求回收率 ≥98%，
分母来自扫描器实际选入回收候选集的密钥，按密钥去重；已发起但失败的计入分母，未发起的单独展示，正常及仅告警对照排除。
例如发起 4000 条、成功 3500 条，回收率为 87.5%，与注入总数无关。回收率独立于速率验收，
实际全回收时显示 100%，不人为插入失败或改写结果。两项均要求对照不误回收、已回收密钥的关联池项与会话完整失效。
扫描器每批最多 5000 条是批容量，不是每秒速率限制；6000 条正常分两批处理，归档每批发起数、成功数和耗时。
回收率不按每秒 5000 条的要求或固定秒数截断，已发起操作完成后核对最终状态；无回收发起时不显示回收率。

速率使用实际回收数除以扫描回收耗时，包含检测与联动写入，不使用 HTTP 受理 TPS；
不含样本准备、清理或链上确认。这是隔离临时表环境测量，不代表生产负载下的持久化吞吐。
测试使用公钥登记元数据故障样本，不生成或接触业务私钥，不证明密码算法本身的安全强度。
扫描器触及的节点、长期密钥、池项、会话、审查记录、批次及链上待办表均被临时表隔离，
结束后关闭连接并清理；逐钥快照和三类异常统计归档在验收服务，可在「验收密钥生命周期」查看。
缺少新版 6000 条样本和实际发起证据的历史结果显示为需要重测。

内部地址通过 `ACCEPTANCE_ABNORMAL_REVOCATION_URL` 配置，Compose 已提供默认值。
该接口仅接受内部令牌和空 JSON 对象，不允许传入业务节点、密钥 ID 或执行参数。
修改后需重建 Django、异常回收 worker、验收后端及网关镜像。

验证：`go test ./...`（backend），`node --test src/utils/test-results.test.mjs src/api/demo-context.test.mjs`（front）。

`KMS_ACCEPTANCE_MYSQL_TEST=1 python tests/test_acceptance_abnormal_revoke_mysql.py`。
